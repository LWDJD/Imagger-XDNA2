# T19 — 256×256 设备门收口(唯一挂账尺寸)

T18 把 256×256 留在"构建就绪、设备门未过":FFN 的 M=288 单 dispatch 在设备上不完成,
改 96 行块后又撞上间歇 ERT state-8。本轮**不重建任何镜像、不改任何算术**——把那条
行块路径跑完、把门补齐,并把 T18 的"~2.6 h/8 步"实测修正为 **59–78 min/8 步**
(重试率随时间波动,见 §4)。

## 1. 本轮做了什么(与 T18 的差异)

* **零镜像改动**:投影 `t7_p5`、ip `t18_ip_m16nd288`(ND=288)、FFN `t11_nh5`(M=96
  行块 ×3)全部复用 T18 已构建/已审计的件;缓存 manifest 逐文件 sha256 由本轮 harness
  在每次跑之前重新校验(9 个文件)。
* **新增证据工具(全部入库)**:
  * `_scratch/image/t19_run.py` — 一次设备跑 + VAE + 13 桶计时闭合 + state-8 计数,
    输出 `<tag>_timing.json`;用 runner 的桶名,可与 WebUI job 直接对比。
  * `_scratch/image/t19_bridge.py` — 产品 `webui/bridge.py` 的薄包装:ckpt
    `next_step>0` 时**不覆盖**检查点,让 `t18_run --resume` 能从中断步续跑
    (2.5 h 的长跑不该被一次硬崩清零);无 ckpt 时走产品原路径。
  * `_scratch/image/t19_gate.py` — 四件套 + 一步门 + 混沌对照,写 `t19_gates.json`。
  * `_scratch/image/t19_chaos.py` — 混沌对照实验(§3.3)。
* **产品侧修了一个真缺陷**:`webui/runner.py` 的设备阶段原来是固定 **1800 s/尝试**
  (128×128 约 97 s),256×256 实测 59–78 min——不修的话 UI 会在第 30 分钟杀掉一个
  **正确**的作业并重试 4 次,即 256 永远不可能从 UI 出图。改为按形状实测 per-layer-step
  缩放(`device_timeout_s`:M=288 → **12,240 s**,1.5× 余量,`ZIMAGE_DEVICE_TIMEOUT_S` 可覆盖)。
  回归:128×128 全链路 job `20261019-015727-f76c23` status done,closure
  sum 93.04 / total 92.39 / unaccounted **−0.65 s** PASS,latents sha16
  `6004035d0cb97250`(与生产逐字节相同)。

### 3.2 模型门:为什么用"一步"作数值门

八步端到端是混沌系统:同一个实现、同一批镜像,64×256(与 128×128 **同一套 M=96 镜像**)
的八步 PSNR 只有 20.70 dB / corr 0.966(T16),而 128×128 是 28.2 dB。终图 PSNR 反映的是
采样轨迹的敏感性,不是内核正确性。所以本轮的数值门是**一步比较**(还没有混沌放大),
八步数字照实报告、不设阈值。

| 比较(同 seed/pe/schedule,一步) | device vs host f32 |
|---|---|
| **256×256**(本轮) | **corr 0.999964**  max\|d\| 0.0802  rms 0.9402 / 0.9396 |
| 128×128(交付路径,同法) | corr 0.999959  max\|d\| 0.0522  rms 0.9368 / 0.9357 |

逐层 host-ref 对比(`--host-ref`,step 0,30 层,每层:设备 attention/FFN 输出 vs 用同一
bf16 输入重算的 f32):

| 形状 | attention rel 中位 | FFN rel 中位 | 备注 |
|---|---|---|---|
| 256×256 | 2.19e-2 | 7.05e-2 | 行误差在 16 行块上均匀(4.1–4.7,只有 32 行 caption 尾部 6.8/9.9),**没有块边界异常** |
| 128×128 | 2.00e-2 | 7.36e-2 | 交付路径基线 |

### 3.3 八步差是采样器敏感性,不是设备误差(混沌对照)

实验(`t19_chaos.py`):把 **设备的一步 latent** 当成起点,用 **host 自己的 f32 算术**跑
第 1..7 步,和两个八步终图比:

    host-from-device-step0  vs  host 八步终图   corr 0.860885
    host-from-device-step0  vs  设备八步终图    corr 0.948083
    设备八步终图            vs  host 八步终图    corr 0.905305

也就是说:把设备那 0.08 的一步差喂给 host 自己,host 也会跑到 0.861——**设备终图落在
host 自身轨迹的散布之内(0.948 > 0.905 > 0.861)**。八步 17.19 dB / 0.905 是扩散采样
对 1e-4 级数值差的放大,不是 256 路径的额外误差。

八步终图数字(如实):latent corr **0.90531**,PNG PSNR **17.19 dB**,mean|d| 0.0715,
latent rms 1.014 vs 1.091。并排图肉眼是同一场景(日出山湖),前景植被不同。

## 4. state-8 实测(修正 T18 §6 的时长)

T18 的估算是"每层 ~2 次重试 → ~34 s/层 → ~2.3 h/8 步"。实测重试是**间歇且成簇**的:
一步可能 60 次重试(1038 s),下一步 0 次(11 s)。8 步合计 **200 / 264 次**,单次代价
7.0 s(等待)+ 10 s(退避)= 17 s,占总 wall 的 **96% / 97%**(3403 / 4493 s)。
所以时长不是 2.3 h 的常数,而是 **59–78 min** 区间(本轮两次)。

* 所有重试都是 `RETRY 1/5`——每个块最多失败一次就过,**从未接近**"同块连续 >20 次"的
  停跑条件(driver 自身 6 次即 REFUSAL,是硬边界)。
* 重试只发生在 FFN 块 dispatch(`ffn RETRY`);attention/projection/ip 全程 0 重试。
* 触发点在**层边界**(每层开头 2 次),与 T18 观察一致;不是 attention 交互
  (T18 `T18_SKIP_ATT=1` 仍复现)、不是 cache-all 内存压力(T18 `--no-cache-all` 仍复现)。
* 根因仍未定位(设备栈行为);本轮把它当**可重试的环境行为**跑完,并证明重试不改变结果。

## 8. 环境事实 / 纪律

* **state-8 是环境行为**:同一进程内重试即过;两次跑的 retry 分布不同而结果逐字节相同,
  这条本身就是"重试透明"的证明。
* **冷启动硬崩**:本轮 6 次设备进程(2 次长跑 + 3 次诊断 + 1 次 runner 回归)全部正常退出
  (rc=0);没有触发 0xC0000005 的收尾崩溃。
* **host f32 与设备跑 #1 并行**(23:09–23:21):可用内存 5.4–6.4 GB(设备 cache-all
  3.71 GB + 投影镜像 1.85 GB + refiner 2.7 GB 常驻,hostref 自身 ~0.8 GB),全程未
  触发 14 MiB 类 OOM;hostref 12 min / 718 s,比 T18 的 27 min 估计快一倍多。
* **.prj 未产生**:没有编译,只有缓存拷贝;`t3d_baseline.py --check` 跑前/跑后均
  `ALL REFERENCE BYTES UNCHANGED`。
* **磁盘**:D: 0.95 GB → **0.933 GB**(新增 cache 938 KiB + 日志/latents 若干 MB);
  未提交任何编译产物(`*.xclbin/*.bin/*.npy/*.npz/*.log` 均在 .gitignore)。
* **不吹**:八步终图 PSNR 17.19 dB 低于 192×128 的 29.86 dB,本文如实列出并给出量化解释
  (§3.3 混沌对照),没有把它写成"更好";官方 256 参考不存在,并排图只有两格。
