* `t22_run.ps1` had no `-Skip`, so it now forwards the engine's existing `--skip` (3 lines, it

  and P06 overwrites them identically when it runs (verified: `doc --check` clean afterwards;
  the RUNBOOK was stale before this and was regenerated by that check).

Read it as three groups:

1. **What the fusion deletes, it deletes completely.** `barrier` is 0.00 on every one of the 480
   fused layer-steps and `swiglu` is 0.00 on every one: the second gu launch, the same-image
   barrier it needed (F-01), and the host elementwise pass are gone.  The second gu C read and
   drain are gone with them: `read` 30.25/36.80 -> 18.15/16.80, `dec` 21.50/23.00 -> 12.85/12.30.
2. **What it adds is the n=160 dispatch.** `gu` 24.40/25.10 -> 46.30/46.40: +21.6 ms/layer for
   the *same MACs*.  That is the documented trap, measured (§4).
3. Net: **-66.9 ms/layer** in the house-recipe pair (median-of-arms), **-43.4 ms/layer** in the
   run_step pair = **-2.0 s/step** and **-1.3 s/step** respectively.  The 8-step loop walls agree
   in sign and bracket it: fused 159.33/148.52 s vs unfused 169.96/201.92 s (the larger pair
   difference is drift -- `u8b` ran in a window 19 % slower than `u8`, which is why the section
   columns, not the wall, are quoted).

That the fusion is a win at all is the FFN section, not the step: the step wall also carries the
projection and the host attention (unchanged by this flag), so -2.0 s/step is -11 % of a 19.4 s
plan step and -7 % of the 27.8 s the plan path measured before PLAN-SPEED-REPORT's fixes.

**The two things that must not move, did not move.**

* delivered default re-run (`del1c`, `run_step -Mode delivered`, AC): `4cc4c6a77d87e728` ==

* unfused plan (re-measured against the same delivered run): **0.995965046**, i.e. the exact
  number PLAN-SPEED-REPORT recorded -- the unfused plan is unchanged.

**Where the divergence enters.** The `[planffn]`/layer lines print `a xm y` per layer:
at layer 0 all four arms are identical (`a 6944.000 xm 725.078 y 97792.0`); at layer 1 the
residual already differs (both unfused runs `735.928`, both fused runs `735.980` -- the fusion
delta is 0.052 there, the harness-to-harness delta 0.0002, so the fusion dominates).  So the
fusion pairs the right tiles and the gu C is the host-silu product to bf16 -- the difference is
the device's tanh silu, exactly what FUSE-GU-REPORT §5 says it is, and it enters at the first
layer the residual carries it.

**Why the gate number is fragile, stated so nobody over-reads it.** Both 1-step numbers are one
seed, one run, and the metric's own spread across arms of this family is `>= 1.3e-3` -- the same
"vs delivered" number reads 0.995965 for the unfused plan, 0.995240 for the fused plan and
**0.994694 for the campaign arm itself** (pGdel vs q2camp).  The difference being judged (7.3e-4)
is smaller than that spread.  At 8
steps -- where the metric has 8 network evaluations behind it -- the fused arm is **closer** to
the campaign arm than the unfused one (0.99585 vs 0.99442).  So the honest statement is: the fused
arm is not *systematically* worse, it is 6e-5 below a hard threshold on the one reference the gate
is defined on, and the threshold (0.9953) was itself derived from the unfused arm's 0.99597.

## 4. The n=160 trap: it is real, and here is what it costs

`pick_n_fused` halves the gu n because the epilogue keeps three C tiles alive (FUSE-GU-REPORT §1):

| | pure gu (n=320) | fused gu (n=160) |
|---|---:|---:|
| n-tiles x k-steps = B objects per dispatch | 32 x 120 = **3,840** | 64 x 120 = **7,680** pair objects |
| dispatches per layer | 2 (gate, up) | **1** |
| B objects per layer | 7,680 | 7,680 |
| bytes per object | 11,520 | 11,520 (2 x 5,760 halves) |
| FLOPs per layer | 166.1 G | 166.1 G |
| **measured `gu` ms/layer (product)** | **24.4 / 25.1** | **46.3 / 47.0** |
| **effective TFLOP/s** | **6.6** | **3.6** |

So the object count per *layer* is unchanged and the object size is unchanged, but a single
dispatch now walks the 64x120 loop issuing two `mm_bfp` per object with a three-tile epilogue,
and it loses **1.86x per FLOP**: **+21.6 ms/layer (+88 %)** for the same MACs.  This is the
object-granularity cost the task asked to watch for, and it is not marginal -- it eats a third of
the 88.5 ms/layer the fusion removes.

**It does not reproduce in isolation, and that is the interesting part.** FUSE-GU-REPORT's
device test measured fused 36.47 ms (4.55 TFLOP/s) vs pure 19.71 ms (4.21), i.e. the fusion was
*slightly ahead* per FLOP.  In the product the pure dispatch runs at 6.6 TFLOP/s (1.6x the
isolated number) and the fused at 3.6 (below it), so the ratio flips from 0.93 to 1.90.  Whatever
the isolated test's BO/queue setup omitted, it is worth 20 ms/layer here -- the fused dispatch is
the one row of this arm that is worse than advertised, and fixing it (a wider n at lower kk, or
letting the epilogue reuse the gate tile) is where the remaining ~1.5 s/step is, not in the host
side.

**Confounds this window had, and the controls that cover them.**  Another session was editing
`webui/shapes.py` / `webui/capability.py` at 21:25-21:26, i.e. between `f8a`/`u8` and
`f8b`/`u8b`, and the box drifted 7-19 % (the P12 speed index moved 1170 -> 1588 MiB/s).  Both are
covered by the design: each arm was run twice straddling that edit and each reproduces **bit for
bit** (`f8a` == `f8b`, `u8` == `u8b`, maxabs 0), so the edit did not touch the numeric path;
the A/B arms are interleaved (fused, unfused, fused, unfused), so drift lands on both; and the
decisive new row, `gu`, is a **device** number (46.3/46.4 vs 24.4/25.1 ms), immune to host load.
What is NOT immune is the absolute `loop_s` -- which is why the loop walls are quoted as a range
(-10.6 .. -53.4 s) and the recommendation rests on the columns, not the wall.

## 5. What the numbers say to do

**Leave `T22_PLAN_FUSE_GU=0`.**  Reasons, in order of weight:

1. **The gate fails as written.** 0.995239938 < 0.9953, and it is worse than the unfused
   arm's 0.995965046 on the same delivered reference in the same harness.  That is the rule the
   task set; a 6e-5 miss is a miss, and the value of the gate is that it is not renegotiated
   after the fact.
2. **The plan path cannot run in the house recipe at all today** (§6), so "arming" it would mean
   shipping a switch whose only valid environment is one the repro tool refuses.
3. The speed it buys (-1.3..-2.0 s/step) is real but it does not change the plan path's standing:
   19.6 -> ~17.6-18.3 s/step against a campaign step of 17.9 s/step, i.e. parity at best, on a
   path that is still not the product default.
4. The one thing that would change the answer is measurable and cheap: **fix the fused dispatch's
   per-FLOP efficiency** (§4) or **re-specify the gate on the 8-step campaign number**, where the
   fused arm is already 1.4e-3 *better* than the unfused one.  Re-running this arm after either
   change is 6 runs and ~25 minutes.

## 6. A blocking defect found on the way: the plan path x the fastglue hooks

With the recipe exactly as shipped (`T22_FASTGLUE=1`, hooks 8/8 installed, `block=on(4 hunks)`),
`T22_PLAN_FFN=1` produces **decorrelated garbage**:

| arm (512² x1, house recipe, AC) | latents | vs the same plan arm with hooks off |
|---|---|---|
| `ph1` plan + hooks ON | `e5f2bd390ab85aed` | **corr -0.013689961**, maxabs 6.22 |
| `u1` plan + hooks OFF | `1e1b8420bb9beda3` | -- |

Mechanism, read off the code and confirmed by the measurement: hunk `h3-ffn-norm1-bf16`
(`install.py:291-300`, gated `_fg_h3 = h3 and ffn_on and devkill`) replaces `_xn` with
`fast_glue.norm_bf16(...)`, which returns a **uint16** bf16 image; `devkill_ffn` consumes that
image (`install.py:838-858`) but `s2_ffn32.ffn32_run` starts with
`x = np.asarray(xn, np.float32)` -- a *numeric* uint16->float32 cast, not a bit reinterpretation.
The plan gets 16256.0 where it meant 1.0.  It does not raise; it silently computes the wrong FFN
for 30 layers and reports `done` -- the same class of silent fallback RUNBOOK §11 is about.
The fix is one line in `s2_ffn32` (a `uint16 -> view(uint32) << 16` branch, exactly what
`devkill_ffn` does), or a refusal in `plan_ffn.register()` when `T22_FASTGLUE=1`.  Until then the
plan arm's only valid environment is `T22_FASTGLUE=0`, which the repro tool's P06 refuses.

Not an argument against this arm (both were measured with hooks off), but it is the reason to
read "plan path" as "plan path with the fastglue hooks off" in every report in this tree, and it
is a blocker for ever making the plan path a product default.
