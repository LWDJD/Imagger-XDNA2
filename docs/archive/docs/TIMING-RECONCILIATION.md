# TIMING-RECONCILIATION.md — reconciling the quoted warm-session-creation times

> Written 2026-10-11 by a read-only audit of the documentation trail.
> **No existing file was modified.** Method: every quoted figure was traced from prose
> back to the raw probe output (`*.log`, `*_out.txt`, `_probe_out/*.json`) and to the
> scripts that produced it. Where a figure could not be traced to a raw measurement,
> this report says so explicitly instead of guessing.
>
> Environment all measurements share: AMD Ryzen AI 9 H 365 (Radeon 880M / Strix XDNA2,
> 8 columns), 31.29 GiB RAM, Python 3.12.11, `onnxruntime-vitisai 1.27.0`,
> providers `['VitisAIExecutionProvider', 'DmlExecutionProvider', 'CPUExecutionProvider']`.
> The cost under dispute is `ort.InferenceSession()` construction for one **2-block
> Z-Image-Turbo DiT shard, 361,820,672 parameters** ("one shard"), with the VAIP
> compile cache already populated.

## 0. Why the documents disagree: there are TWO shard builds and MANY machine states

The single most important fact the prose never states side by side:

| build | env var | geometry | layer-shard S | ONNX storage | ONNX size/shard | `.rai` size/shard | per-session RSS |
|---|---|---|---|---|---|---|---|
| **A** | `ZIMAGE_SHARDS_DIR=_probe_out\shards` | **128×128** | **S=96** (64 img + 32 cap, `ROUTES.md:77-80`) | **fp32** | 1.348 GiB (1,447,405,339 B) | 399.5 MiB (418,882,224 B) | 0.902 GiB |
| **B** | `ZIMAGE_SHARDS_DIR=_probe_out\shards_i1024_c32` | **512×512** | **S=1056** (1024 img + 32 cap) | **fp16** | 0.674 GiB (723,733,155 B) | 485 MiB (508,246,552 B) | 1.154 GiB |

Both builds contain the **same 2-block layer shards with identical parameter counts**
(361,820,672). Sources: `ROUTES.md:55-59, 77-80, 89-96`; `_sessbreak128.log:2`
("shard set shards img_tokens=64 cap=32"), `_sessbreak.log:2`
("shard set shards_i1024_c32 img_tokens=1024 cap=32"); `MEMORY-AND-TIMING.md:57-60`
(S=96 → 0.902 GiB/session, S=1056 → 1.154 GiB/session);
`BFP16-VERDICT.md:103-115` (`.rai` 508,246,552 B at S=1056 vs 418,882,2xx B at S=96,
same 407,048,256 B of BFP16 weights); `SESSION-COST-ATTRIBUTION.md:20, 29-31`.

**Measured warm-creation times differ by up to 2× between the two builds, on the same
machine, four minutes apart** (see §4, the `_sessbreak` pair). Almost every quoted
"per-shard" figure is silently build-specific.

Second axis: **machine-state drift**. The project's own anchor measurement
(`MEMORY-AND-TIMING.md:8`, `:165`) shows the *same shard, same code path* at
**17.29 s with 21.25 GiB available** (`_attrib.log:22`) versus **24.26 s with 14.7 GiB
available** (`_anchor_pre.log:22`) — a 40 % swing; `SESSION-COST-ATTRIBUTION.md:82`
records one shard spanning **19.24 / 20.15 / 19.99 / 24.41 / 25.32 / 26.04 s**
(a 6.6 s range on one shard, one code path); `_runcheck.log:27-30` (128-geometry run,
2026-10-09 08:12) shows 26.2–39.6 s per session while `_firstrun.log:19` the same
morning at 10:44 shows 17.51 s.

Third axis: **cold vs warm**. This one is cleanly separated in the evidence and is
*not* the source of any contradiction:

| VAIP cache state | measured per-shard session creation |
|---|---|
| **COLD (compiling)** | 128-geometry layer shard **350–380 s** (`HANDOFF.md:319`), 353.8 s (`HANDOFF.md:347`), "首编 5.8 min" (`STATIC-SHAPE-ENGINEERING.md:89`); 512-geometry layer shard **764.5 / 777.6 / 1173.1 / 1193.1 s** (`HANDOFF-512.md:135-140`, quoted as "约 780–1200 s/片" at `:119`); 3-block 1024-geometry 995.5 s (`SINGLE-GRAPH-LIMITS.md:102`); YOLOv4 whole net 1973.97 s (`YOLO-ON-NPU.md:37`) |
| **WARM (cache hit)** | **10–26 s**, depending on build and machine state (this report) |
| cold corrupted by lid-sleep | `layers_06_08` **2026.2 s**, "被合盖挂起拉长" (`HANDOFF-512.md:138`; "从约 770 s 拉到 2027 s" `HANDOFF-512.md:166`) |

**Every figure in the contradiction list is a WARM measurement.** None of them is a
disguised cold compile, so cold-vs-warm does not explain the spread.

## B. Recommended authoritative number

### B.1 What to quote

Because the two builds differ by up to 2×, there is no single honest number. Quote it
as a function of build and machine state:

> **Warm VAIP-cache `InferenceSession()` construction of one 2-block shard
> (361,820,672 params), serial, one process:**
>
> * **build A (128×128, S=96, fp32-stored ONNX):**
>   **15–18 s on an idle machine** (17.51 s `_firstrun.log:19`; 17.29 s `_attrib.log:22`;
>   15.67–15.88 s `_probe_out/parallel4.txt:21-24`; 14.2–16.1 s `_probe_out/batch.log:68-84`),
>   **22–26 s during a full 17-session resident build** (22.1–26.2 s `_prof128.log:27-43`,
>   24.3–26.6 s `_sessbreak128.log`; mean **25.0 s** = 425.5 s / 17),
>   **up to 26–40 s on a loaded machine** (`_runcheck.log:27-30`).
> * **build B (512×512, S=1056, fp16-stored ONNX):**
>   **10–13 s idle** (10.3–12.8 s `_repro512b.log:27-43`, mean 11.36 s),
>   **11–17 s typical** (11.2–16.8 s `_sessbreak.log`), 10–18 s under LRU thrash.
>
> **Single planning number for the production 128-geometry pipeline: 25 s/shard
> (= 425 s to build all 17 resident sessions).** Single number for an isolated probe
> on a quiet machine: **~16 s/shard**. For the 512-geometry build: **~11–14 s/shard**.

If a downstream document must state one scalar without qualifiers, use
**"15–26 s warm, build-dependent"** and keep 25 s only as the *pipeline-startup* value.

### B.2 Why the discarded figures are wrong

* **25.00 s is not a measurement** (`CONVERSION-COST-ANALYSIS.md:18`). Its own raw
  backing (`_probe_out/session_cost.json:5`) says "20 measured runs, 15–25 s spread",
  and `analyze_session_cost.py:43-58` merely hard-codes `warm_s` values and computes
  rates. Two decimal places on "25.00" and on "14.47 M elem/s" are artifacts of that
  arithmetic. Additionally the one raw 4-creation experiment behind the "25 s" story
  (`probe_vaip_cache_hit.py`) actually timed **context_refiner**, and the same script's
  context_refiner measurements elsewhere (`SESSION-COST-ATTRIBUTION.md:73`) have mean
  19.69 s. Use the 15–25 s envelope the note declares, not 25.00.
* **15.7 s is a quiet-machine point, later measured 40–65 % slower.** Same code path:
  18.1–26.0 s on 2026-10-07 evening (`SESSION-COST-ATTRIBUTION.md:143-144`,
  `NPU-SPEEDUP-ROUND1-BLOCKED.md:86-88`), 22–26 s in the 17-session run of 2026-10-09.
  Quoting 15.7 s for startup planning understates the observed 425 s / 17 = 25.0 s.
* **10–18 s and 10–12 s are build-B numbers.** All three raw runs behind them
  (`_repro512.log`, `_repro512b.log`, `_prof3.log`) print `512x512` and use
  `shards_i1024_c32` (fp16-stored ONNX, S=1056). Applying them to the fp32-stored
  2-block shard conflates two builds that differ by ~2× on the same machine
  (§4). Note also the brief's attribution slip: `BFP16-UNLOCKED.md` says **~25 s/分片**,
  the 10–18 s lives in `BFP16-VERDICT.md` / `ROOT-CAUSE-SILU-ORDER.md` / `ROUTES.md`.
* **10–35 s is an envelope with an untraceable upper bound** and a wrong mechanism
  gloss ("读 485 MiB ≈38 MB/s"): measured disk read of a 1.32 GiB shard file is
  0.228–0.248 s at **5,928 MiB/s** (`SESSION-COST-ATTRIBUTION.md:33-34`), so reading a
  485 MiB `.rai` cannot cost 12.8 s. The 12.8 s is single-core CPU work plus session
  init (see B.3).
* **425.5 s / 17 = 25.03 s is correct but is an average over a drifting run**
  (22.1 s first session → 26.2 s sixteenth as available RAM falls 20.1 → 5.3 GiB).
  It is the right total for pipeline planning; it is not a per-shard constant.
* **`SINGLE-GRAPH-LIMITS.md` internally contradicts itself** (its 10–12 s/shard is
  build B, its 425 s / 8.67 s wall-clock line is build A, `:108` vs `:126`). Only the
  10–12 s belongs to that document's 1024-token configuration.

### B.3 What the warm cost *is* (measured vs inferred)

Measured (all agree):

* 87 % of it is VitisAI-EP-side; ONNX parse 12 %, disk 1 %
  (`SESSION-COST-ATTRIBUTION.md:46-50`).
* It is single-core CPU work: 90–102 % of one core, wall time ≈ CPU time
  (20.15 s wall / 20.38 s CPU, `:55-56`; `_attrib.log:22` "17.288s wall cpu 17.359s
  (100 % of one core)").
* It is **not** a compile: cache writes "0 new, 0 modified" during creation
  (`SESSION-COST-ATTRIBUTION.md:41`, `_attrib.log:24`, `SINGLE-GRAPH-LIMITS.md:109`);
  an empty `XLNX_CACHE_DIR` costs the same 25.6 s and writes 0 files
  (`STATIC-SHAPE-ENGINEERING.md:81-88`); a true cold compile is 350–1200 s.
* It is **not** a cache miss, and it is **not** disk.
* It is **not** re-packing the `.rai` on disk: 42 `.rai` files byte-identical
  (size/mtime/hash) before and after session creation (`HANDOFF-CURRENT.md:112`,
  `ROUTES.md:33`).
* It is roughly constant over session index N = 1…4 (`SESSION-COST-ATTRIBUTION.md:93-110`)
  and does not parallelise (threads arm = ×1.01, §5).

Inferred (unproven, and mutually inconsistent in the docs):

* `HANDOFF.md:532-535` calls it "VAIP 对全部 3.62 亿个权重做的逐元素准备工作，
  发生在缓存查找之前" (per-element weight preparation before the cache lookup).
* `HANDOFF-CURRENT.md:113` calls it "读 485 MiB 产物 + NPU 会话初始化" (read + init).
* `BFP16-VERDICT.md:125-126` calls it "VAIP 把 fp32/fp16 权重现场打成 BFP16 并装载 .rai".
* `HANDOFF.md:3641` correctly records the honest status: "**推断，未直接测到** …
  EP 自带的报告文件不含耗时字段". All three attributions are guesses; only the
  measured facts above should be quoted.

**Answer: no.** The "~58 ns/element (14.5–20.0 M elem/s)" law
(`CONVERSION-COST-ANALYSIS.md:25-27, 165`) holds only for its own sample of three
fp32-stored >50 M-param models (its own words: "规模跨度 6 倍的大模型上，速率稳定在
14.5–20.0 M 元素/s（离散度 1.4×）"). Across the project's own Z-Image measurements the
rate spans **14.3–31.9 M elem/s (31–70 ns/elem), a 2.2× spread**, and the fastest values
come from the fp16-stored build B — **the same 361.8 M elements created ~2× faster than
build A** (`_sessbreak.log` 2026-10-09 10:23 vs `_sessbreak128.log` 10:27, same script,
same process structure, 4 minutes apart). That is direct evidence that the cost is not
purely per-element: initializer **bytes** (fp32 1.35 GiB vs fp16 0.72 GiB, ratio 1.87)
fit the observed 1.8–2.2× ratio better than element count (ratio 1.00). This also
undermines the project's "fp16 存储没用（量化按元素个数算）" claim
(`HANDOFF.md:628`, `CONVERSION-COST-ANALYSIS.md:38-39`): that claim is derived from the
per-element model, not from an A/B of session creation between the two builds — and the
two builds *are* the A/B, with the fp16 one being faster. (Caveat: S and graph contents
also differ between the builds, so bytes vs. S cannot be fully separated — see §D.3.)

The safest published rate statement: **~70 ns/element for fp32-stored shards on a
loaded machine, ~31–48 ns/element measured on quiet machines and on the fp16-stored
build; small graphs are dominated by a fixed per-session overhead and are not on this
law at all.**

## D. Figures that CANNOT be reconciled from the available evidence

1. **The "280.3 s / ~270 s session loading / TOTAL 4.04 s" 128-geometry run**
   (`ROUTES.md:28`, `:150`; `ROOT-CAUSE-SILU-ORDER.md:188-196`). No raw log of a run
   printing "generated in 280.3s" exists anywhere in the tree (searched all `*.log`,
   `*.txt`, `*.json`, `*.md`). Its derived per-session time (270 s ÷ 17 = 15.9 s) is
   plausible and near `batch.log`, but its "TOTAL 4.04s" one-pass NPU compute conflicts
   with the same-build 8.67 s (`_prof128.log:75`) for the same 8-step/17-shard workload,
   and `ROUTES.md:152-154` shows the attribution line "17 (100.0%) / NPU executed 17
   subgraph(s)" where an 8-step 128 run gives 136 (`_prof128.log:73-75`). The run's
   step count, geometry mix, and even existence cannot be verified. **Do not cite 280.3 s
   as evidence for a per-session rate.**
2. **The "35 s" upper bound of "10–35 s"** (`HANDOFF-CURRENT.md:113`). The nearest raw
   numbers are 30 s ("每个 11–30 s 的单线程权重打包", `HANDOFF-512.md:95`, build-B
   reloads) and 39.6 s (`_runcheck.log:27`, build A). No measurement of 35 s exists.
   The bound is a rounded sentiment, not data.
3. **Whether build A vs build B's ~2× gap is caused by fp16-vs-fp32 initializer storage
   or by graph differences (S=96 vs S=1056 node sets/txn bins).** The two change
   together in every available run; `probe_slen_scaling.py` (which would have held
   storage constant and varied S) was written but its outputs (`_probe_out/slen_*`) are
   gone. Unresolvable; flagged as contradicting the per-element law instead.
4. **The "21.0 s" for `context_refiner` in `session_cost.json:13`.** No raw measurement
   of 21.0 s exists. Every measured context_refiner creation is 14.2 / 15.0 / 17.29 /
   19.24–26.04 / 23.1–24.0 / 25.5 s. The value is a fabricated midpoint (its note says
   only "warm; slightly fewer params, no adaLN").
5. **`HANDOFF.md:500-503` ("那 12 秒", "每 layer 分片 1.809 亿参数 ÷ 12 秒 ≈ 1500 万
   元素/秒")** cannot be reconciled with `HANDOFF.md:513` (same layer shard =
   361,820,672 params = 3.62e8) — the param count is exactly half — and the "12 s" is
   itself a CPU-EP-vs-NPU *difference* (14.43 − 2.38 s, `HANDOFF.md:498`), not a session

6. **Provenance of `HANDOFF.md:318`'s "15.74 s"** as a *named* measurement: it equals

## 5. `_probe_out/parallel_session.json` reconciled

Raw text: `_probe_out/parallel4.txt` (probe `probe_parallel_session.py`,
2026-10-07 08:05). Shards `layers_00_02 … layers_06_08`, **build A (S=96)**, warm VAIP
cache, page cache pre-warmed (5.39 GiB read in 1.40 s), available RAM 20.30 GiB,

|---|---|---|---|---|
| serial | 15.74 / 15.67 / 15.88 / 15.88 | 15.79 | 63.31 s | consistent with `batch.log` (15.12 s mean) and `_firstrun.log` (17.51 s) on a quiet machine |

Reconciliation against the headline figures:

* These 15.67–15.88 s values **are** the quiet-machine build-A regime — they sit inside
  `batch.log`'s 14.2–16.1 s and below `SESSION-COST-ATTRIBUTION.md`'s 19.24–26.04 s
  (the latter was measured 12 h later under documented external load).
* They are **4 sessions with peak RSS 4.23 GiB** (JSON `notes.per_session_gib_measured`
  0.88); do not extrapolate "15.8 s × 17 = 269 s" as pipeline startup. The real
  17-session build of the same shards measured 22.1–26.2 s per session
  (`_prof128.log:27-43`, 425.5 s). The JSON's own `baseline_note` — "serial arm

* The thread arm is the decisive evidence that in-process parallelism cannot amortize

* Correctness check in the JSON (`verify.worst_rel` 0.0499) matches the build-A per-shard
  rel table (`HANDOFF.md:260-262`: layers_02_04 4.267e-02, layers_04_06 3.217e-02,
  layers_06_08 4.991e-02), which independently confirms these were the renamed-I/O
  build-A shards, not build B.
