## 1. 原始问题的诊断（已完成）

用户最初的问题：「无法完成单 BlockFP16 权重轻量出图，只能运行前长时间编译，然后 NPU 计算，CPU 计算时长占比 >95%，且不是算子回退导致」。

### 根因（实测确认）

| 现象 | 真相 |
|---|---|
| CPU >95% | **建会话的逐元素权重准备**，不是算图。实测 425.5 s 建会话 vs 8.67 s NPU 计算 = 97.8% |
| 「不是算子回退」 | ✅ **用户判断正确**。`declined.json` 无 CPUExecutionProvider 键，625 节点融成 1 个 NPU 节点 |
| 「运行前长时间编译」 | **混了两件事**：真编译（350–1200 s/片，一次性，缓存在 `.rai`）+ 建会话（10–26 s/片，每次都要）。后者是大头 |
| 为什么看不见 | **计时盲区**：`zimage_pipeline.py:252-254` 只计 `sess.run()`，`session()` 建会话的时间只 `print` 不累加 |

### 已证伪的路线（不要再投入）

| 路线 | 结论 |
|---|---|
| **并行建会话** | ❌ **死路**。EP 全局锁，4 线程并发 62.91 s vs 串行 63.31 s，零加速 |
| fp16 存储省时间 | ❌ 文档说无效——**但这是错的**，见 §2 更正 |
| 合并分片省内存 | ⚠️ 文档的论证有缺陷（fp32/BFP16 驻留混测，截距 −1.85 GiB 物理不可能） |
| `wgt_formatting` 打包 | ❌ AMD 工具明确拒绝 BFP16：`Unsupported OP type: MatMul_bfp16xbfp16xbfp16` |
| 直接喂 BFP16 给 Gemm | ❌ ONNX 类型系统拒绝（见 §5） |

## 3. 三个关键 bug（都是静默错算，不是崩溃）

### 3.1 RoPE 完全缺失 ⚠️ 最严重

`build_meta_model()` **从不调用** `patch_forward_real_rope` / `patch_processors`。于是 `wrap_shard` 的块收 `freqs_cis=None` → **旋转整段被跳过**。

**证据**：换掉 cos/sin，torch 参考输出**逐位不变**（rel 0.0）。

**影响**：项目里所有基于 `wrap_shard` 导出的图**都不含 RoPE**——包括原计划的 17 个 fp32 分片。所有「与 PyTorch 参考一致」的验证都只覆盖了无旋转路径。**若没发现，会产出位置信息全错的图且所有验证都说对。**

**修复**：`export_skeleton.py` 现在打两个补丁并断言替换数 > 0：
```python
from export_dit import patch_forward_real_rope, patch_processors
patch_forward_real_rope(model, per_axis_cos, per_axis_sin, bsz=1)
n_proc = patch_processors(model)   # 断言 n_proc > 0
```
**验证**：cos/sin 成为真图输入、输出对 RoPE 敏感（0.405）、与参考吻合（1.70e-02）。

### 3.2 `safetensors.get_tensor` 访问违例

`WeightStreamer.read` 用 `h.get_tensor(k)` 会崩（`0xC0000005`，`torch/storage.py:354 __getitem__`）。

**排查结论**：文件完好（裸读正常），是**库路径的问题**。
**修复**：`shard_lib.WeightStreamer.read` 改为按 safetensors 头部偏移裸读字节构造张量。

### 3.3 `do_constant_folding=False` 是致命前置

项目为绕 protobuf 的 fp16-Cast 路线**故意关了**常量折叠。但权重转成图输入后，VAIP 看到 unranked 类型，FlexML 断言崩溃：
```
Assertion failed: (*this).hasRank() && "cannot query rank of unranked shaped type"
```
**修复**：会话创建时用 `ORT_ENABLE_ALL`。这也呼应「ORT 折叠 655→208 节点」的发现。

## 6. BlockFP16 格式规格（逐字节逆向，已验证）

```
打包流 = W (N,K) 行主序、K 连续、每 8 元素一组
每组 9 字节 = [指数字节][8 × int8 尾数]

e = E'−7  (amax 恰为 2 的幂)
  = E'−6  (否则)          ← E' = amax 的 IEEE 无偏指数；用位型，勿用 log2
尾数 = sign(q)·floor(|q| + 0.5)    ← 远离零舍入（−50.5 → −51）
若 m.max() > 127 则 e += 1          ← +128 溢出才升档，−128 合法
指数字节 = (e + 133) & 0xFF         ← 即 IEEE 偏置 127

排列 = tile_rows 行 × 32 K元素 为一个 tile
tile 内 slot = (r//8)×32 + (c//8)×8 + (r%8)
             其中 r = row % tile_rows,  c = kelem % 32
全局 slot = tile_index × (tile_rows/8 × 32) + slot_in_tile
```

**`tile_rows` 是 (N, K, M) 的函数**，无预测规律（非单调），由编译器 `L2ToL3TilingAnalysisPass` 决定。**12 种形状的值在 M=64 下已全部实测**，见 `pack_bfp16.KNOWN_TILE_ROWS`：

```python
(3840, 15360): 32,  (10240, 3840): 32,  (15360, 3840): 48,
(15360, 256): 64,   (3840, 256): 48,    (64, 3840): 16,
(3840, 64): 80,     (3840, 2560): 32,   (1024, 256): 64,
(256, 1024): 64,    (3840, 3840): 48,   (3840, 10240): 32,
```

⚠️ **换分辨率（不同 M）打包生产权重前，必须在那个 M 上重新测 `tile_rows`**。`detect_tile_rows(W, blob)` 可自动探测（全区逐字节验收）。

**张量清单**（`ZIMAGE-TENSOR-INVENTORY.md`）：521 张量 / 6,154,908,736 参数，账目精确。GEMM 权重只有 **6 种 (N,K) 形状**。

## 7. 性能现状与瓶颈

> ⚠️ **本节已于 2026-10-12 被 `MEM-PROFILE.md` 实测推翻。下面的「更正后」是当前正确版本，
> 保留「原始结论」只作对照。任何性能判断请以 `MEM-PROFILE.md` 为准。**

| | fp32 权重 | BlockFP16 权重（当前） |
|---|---|---|
| 磁盘 | 22.885 GiB | **6.439 GiB** ✅ |
| 出图耗时 | 468.4 s | **1098.3 s** ❌ |
| NPU 计算 | 69.32 s | 66.85 s |
| 会话驱逐 | 134 | — |

### 7.1 更正后（实测，`MEM-PROFILE.md`）

**（a）重载耗时的 94.5% 是权重解包，不是建会话。**

| 项 | 耗时 | 占比 |
|---|---|---|
| `ort.InferenceSession()` | 0.52 s | 5.5% |
| **`_load_weights()`（解包）** | **8.86 s** | **94.5%** |

`skeleton_runner.build_times` **只计会话构建**，所以此前打印的「session X: xx s」
**漏掉了大头**。这与 §1 的计时盲区是同一类错误，只是发生在另一个字段上。

**（b）BFP16 从不以 BFP16 形态驻留 RAM。**
`pack_bfp16.unpack()` 返回 `float32`，`skeleton_runner._load_weights` 再 `.to(torch.float32)`
后缓存进 `self.weights`。所以：

> 磁盘省 4 倍，**RAM 一分没省（仍是 22.9 GiB）**，还白付 272 次解包。
> 这就是 BFP16 那次 1098 s 比 fp32 468 s 更慢的全部原因。

**（c）会话内存不是瓶颈，且 lean 选项无效。**

| | stock | lean |
|---|---|---|
| 17 会话全驻留 | **2.42 GiB** | **2.45 GiB** |
| 边际/片（第 4 片起） | ≈0.01 GiB | ≈0.01 GiB |

15 个 `layers_*` 结构完全相同，ORT/VAIP 共享缓冲规划，第 4 片起几乎不增加内存。

**（d）预算表**（可用 14.48 GiB）：

| 方案 | 会话 | 权重 | 合计 | 判定 |
|---|---|---|---|---|
| fp32 驻留 + cache=17 | 2.42 | 22.92 | **25.3 GiB** | ✗ 超 10.8 GiB |
| **packed BFP16 驻留 + cache=17** | 2.42 | **5.73** | **8.15 GiB** | ✅ 余 6.3 GiB |

**结论：会话内存、lean 选项、分片数都不是变量。唯一变量是「权重以什么形态驻留 RAM」。
让 EP 直接吃 packed BFP16（路由 ①②③）是唯一出路，不是优化。**

### 7.2 原始结论（已被推翻，仅作对照）

> ~~瓶颈不是转换，是 LRU 抖动：17 分片循环访问 + `cache<17` = 命中率恒为 0。
> 总权重内存不随分片数变化。fp32 常驻 24.6 GB 装不下；BFP16 常驻 6.45 GB
> 装得下 → cache=17 → 无抖动 → 预计 <20 s/图。~~
>
> **错在两处**：(1) BFP16 根本不以 BFP16 形态驻留；(2) 漏算会话内存与解包成本。
> 「LRU 抖动导致重载次数多」这部分仍然成立。

## 8. 下一步（按优先级）

> ⚠️ **优先级已按 `MEM-PROFILE.md` 的实测重排。** 原计划把「压缩分片数」
> 当成独立收益——**内存上它无效**（权重字节数与分片数无关），只对减少重载次数有意义。

### 8.1 让 EP 直接吃 packed BFP16 ★唯一出路

实测：RAM 25.3 GiB → 8.15 GiB 的**唯一**手段（`MEM-PROFILE.md` §3）。

已测：`Gemm` 直接收 `BFLOAT16`/`UINT8`/`UINT16` 权重**都被 ONNX 类型检查拒绝**（图加载阶段，0.003 s，EP 未参与）。

**路线 ①：加 Cast 骗过类型检查**
```
W_u8 [N·K·9/8] ──Cast──> W_f32 [N,K] ──Gemm──>
```
关键看 EP 是否把 Cast **折叠进权重缓冲**（直接 DMA 到 `coalesed_weights`）还是老实转换。
**改动最小，先试这个。**
⚠️ 注意：权重是**图输入而非 initializer**，ORT 的常量折叠对图输入无效，
所以「optimizer 折叠 Cast」只在 initializer 路线上成立（那条会撞 2 GiB protobuf 上限）。

**路线 ②：AMD 自定义算子**
`register_castavx.cpp` / `register_dynamicdispatch.cpp` 在本 EP 已注册（日志已确认每次启动都打印
`Running CastAvxOpRegister::register_ops`），即 `BF16_to_BFP16`、`MatMul_noqdq` 可用。
它们是 DD 路线处理 BFP16 权重的方式。**若路线 ① 的 Cast 不被折叠，走这条。**

**路线 ③：`.rai` 权重区注入**
`.rai` 带权重时（44 MB/片）**feed 被忽略**，`.rai` 供权重。打包器已 100% 验证。

> ★ **2026-10-12 新发现（已验证）：完整性校验是「比对」而非哈希 —— 路线 ③ 很可能可行。**

**（a）校验是比对，不是对 `.rai` 求哈希。**
来源：`onnxruntime_vitisai_ep.dll`，错误串 `Model cache file is corrupted or not compatible` 附近（偏移 ~63,380,240）；
DLL 内嵌源码路径 `G:\xmc\src\voe\vaip\vaip_pass_vaiml_passes\vaip_vaiml_common\vaiml_cache.cpp`。校验流程字符串（按序）：

```
Checking model cache status...
    Checking model cache file:
    Found model cache
    Checking context JSON:            <-- 校验点
    Verified model cache:
Model cache file is corrupted or not compatible:
. Please re-run with --force option to re-generate model cache.
```

另有 `Model signature: `。**整个 DLL 不含任何 md5/sha1/sha256/blake 字符串**（唯一哈希样符号是 Cython 的 `__pyx_checksum`，属 Python 绑定模块自检，无关）。

**（b）`.rai` 尾部结构（已完全解码）**：

```

<flatbuffer vtable: 08 00 0c 00 04 00 08 00 08 00 00 00 08 00 00 00>
2c 00 00 00  20 00 00 00  <digest_A: 32 位小写十六进制>  00 00 00 00
```

> **原地覆写权重区、文件长度不变、尾部不动 → 应当通过校验。**

此前 `probe_inject_weights.py` 注入失败（报 "corrupted or not compatible"）——但那次把文件从 365,904 B **撑大**到 44,550,144 B，尾部被毁掉。
