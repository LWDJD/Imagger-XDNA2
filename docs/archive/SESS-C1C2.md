# SESS-C1C2 — 17.4% 的来源：bfp16 量化地板，不是累加漂移，也不是我方参考错

> t22_sessA 第四轮（2026-10-24）。父任务批准 C1/C2：解清 17.4%，否则一切免谈。
> 结论：**解清了，而且是好消息——这条路径的数值与我们自己的 bfp16 路线同一量级。**

## 0. 结论先行

1. **17.4% 是 bfp16ebs8 的输出量化地板，不是 16 位累加的漂移。**
   三条独立证据：①NPU 输出是 **2⁻⁷ 的整数倍**（1.4375=184/128、0.4844=62/128、0.625=80/128…）；
   ②**常量输入**（x≡3.25，LN 解析解恰为 0）→ NPU 输出 max|y| = **0.0078125 = 2⁻⁷**；
   ③相关性 **0.999977**、均值 −0.000003、std 1.00176（参考 0.999995）——**算子语义完全正确**。
2. **误差随深度增长是传播，不是失控**：LN 单算子 mean 0.0055 / max 0.0601 → 全链 mean 0.0142 / max 0.133。
3. **这和我们自己的 bfp16 路线是同一个数值类别**（README 记的 NPU bfp16 matmul rel 1.01e-02）。
   所以"官方 DD 路线精度不够"这个判断**不成立**——它的地板就是 bfp16 的地板，双方一样。
4. 但 **0.5% 口径与 bfp16 的冲突是真的**，只是它**不只针对官方路线**，也针对我们自己的产品。
   这是负责人该拍的"速度 vs 精度"裁决，而不是"选哪条路线"。

### 1.1 为什么判定是量化而不是漂移

**证据 A —— 输出落在 2⁻⁷ 网格上。** 最差那一行的前 6 个值：

```
NPU : 1.4375   0.4844   0.625    -0.1719   0.0625   0.0
REF : 1.4288   0.4873   0.6249   -0.1719   0.0692  -0.0065
比值: 1.0061   0.9941   1.0002    0.9999   0.9035   -0.0
```

1.4375 = 184/128、0.4844 = 62/128、0.625 = 80/128、0.0625 = 8/128 —— **全是 1/128 的整数倍**。
bfp16ebs8 每 8 个元素共享一个指数、8 位尾数 ⇒ 步长 = 2^(块指数−7)。这就是 bfp16 的网格。

**证据 B —— 解析解为 0 的输入。** `x ≡ 3.25⟧ 时 LN 输出恒等于 0；NPU 给出 **max|y| = 0.0078125 = 2⁻⁷**。
误差恰好是**一个量化步**，不是累积漂移（漂移会随 K 增长，这里与 K 无关）。

**证据 C —— 语义正确。** 相关性 0.999977、std 归一化正确、均值归零。
如果是算子实现错误（epsilon 不同、gamma 位置错），相关性与矩都会明显偏离。

### 1.2 与全链对照

| 图 | 误差 mean | 误差 max | 相对 rms(max) |
|---|---:|---:|---:|
| 纯 LayerNorm | 0.0055 | 0.0601 | 6.0% |
| 全链（LN→GEMM→Add→Gelu→GEMM→Add） | 0.0142 | 0.133 | 17.4% |

两层 GEMM（K=1536 与 K=6144）把单算子的量化误差放大了约 2.6×（mean）——**这是量化误差经过线性层的正常传播**，
不是数值失控。

## 2. C2 — acc16bfp 确认

### 2.1 命名证据（逐字）

事务库里 1,233 个 gemm 与 64 个 layernorm 的命名（`sd_fastpm_DiT.zip⟧）：

```
gemm_a16bfpw16bfpacc16bfp_1_1024_1536_6144.bin      <- B=1 M=1024 K=1536 N=6144
gemm_a16bfpw16bfpacc16bfp_1_1024_6144_1536.bin      <- 第二层 GEMM
layernorm_a16bfw16bfacc16bfp_1_1024_1536.bin
```

`a16bf⟧ = 激活 16 位 bfp、`w16bfp⟧ = 权重 16 位 bfp、`acc16bfp⟧ = **累加器 16 位 bfp**。
**整条路径端到端都是 bfp16**，没有一处 fp32。

### 2.2 实测与命名一致，但主项不是累加

父任务的原假设是"acc16f 的抵消误差 ∝√K"。**实测不支持这个机制为主因**：
- 常量输入测试中误差 = **恰好一个量化步**，与 K 无关；
- 输出网格是 2⁻⁷，这是**输出量化**的签名，不是累加漂移的签名（漂移会给出连续分布，不会落在网格上）。

**准确表述**：误差 = **输出/权重的 bfp16 量化**（主项）+ **16 位 bfp 累加**（次项，深链时叠加）。
所以"acc16bfp 属实"成立，但把它当成 17.4% 的唯一原因是**归因过窄**。

## 3. 对产品裁决的意义（这是本轮最重要的输出）

| | 官方 DD 路线 | 我方 bfp16 路线 |
|---|---|---|
| 权重格式 | `w16bfp⟧（bfp16ebs8） | `bfp16ebs8⟧（同一格式） |
| 激活 | `a16bf⟧（bfp16） | bf16 激活 + bfp16 权重 |
| 累加 | `acc16bfp⟧（16 位 bfp） | 我方是 bf16 累加 |
| 实测地板 | LN mean 0.55% / 全链 mean 1.4% | README：rel 1.01e-02（≈1%） |
| 会话启动 | **0.23 s** | 27.7 s loop |

**两条路线的精度地板在同一量级（≈1%），差别不在精度而在速度与可控性。**
因此父任务预设的"若 acc16f 属实 ⇒ 官方路线与我们 0.5% 口径冲突"——**冲突确实存在，但它同时打两条路线**：
**0.5% 不是"选官方还是选开放"能解决的问题，是"要不要坚持 0.5%"的产品决策。**

建议呈负责人的问法（三条，互斥）：
1. **守住 0.5%** ⇒ 两条 bfp16 路线都不合格，需要 fp16/bf16 权重路线（放弃 1.125 B/param 的压缩收益）；
2. **放宽到 ≈1.5%（mean）** ⇒ 两条路线都合格，此时**应选官方 DD 路线**（启动 0.23 s vs 27.7 s）；
3. **分阶段**：先用官方 DD 路线拿到"快"，精度另立专项。

## 4. 稳定性副产物（必须记）

EP 路径在**进程退出时**会以 `0xC0000005⟧（ACCESS_VIOLATION）崩溃——本轮 3 个脚本都在**打完结果之后**死掉。
数据不受影响，但**服务化必须先解决这个 teardown 崩溃**，否则每次重启都是一个崩溃事件。
与 E1 的 `0xC0000409⟧（load_state 缺失文件）是**两个不同的崩溃点**，都要进 B2 的健壮性清单。
