## 1. C3 — 规模验证

### 1.1 方法

用**官方事务库覆盖得到的 shape** 造多子图图：每个分支 = LN → MatMul(W_up[1536,6144]) → Add → Gelu → MatMul(W_dn[6144,1536]) → Add，
分支共享同一组权重（所以文件只有 75 MB），各分支独立输出。经 `sd3_mmdit_bfp.yaml⟧ 分区后，每个分支产生 **1 个 DynamicDispatch 子图**。

### 1.2 实测

| 分支数 = 子图数 | 分区 | 会话（首进程） | 会话（后续进程） | 单次 run | 节点归属 |
|---:|---:|---:|---:|---:|---|
| 1 | 5.6 s | 0.291 / 0.237 s | — | 0.16 / 0.13 s | 3/3 EP |
| 4 | 6.3 s | 0.276 / 0.304 s | — | 0.16 / 0.14 s | 9/9 EP |
| 8 | 8.3 s | 1.644 s | 0.301 s | 0.22 / 0.18 s | 17/17 EP |
| **16** | 11.9 s | **3.263 s** | **0.381 / 0.408 s** | 0.29 / 0.26 / 0.24 s | 33/33 EP |
| **26** | 24.6 s | **5.752 s** | **0.564 / 0.436 s** | 0.37 / 0.29 / 0.28 s | 53/53 EP |

**两种成本要分开**：
- **warm（后续进程，页缓存热）**：0.25 → 0.50 s，**几乎不随子图数增长**；
  拟合 **`session ≈ 0.24 s + 0.010 s × 子图数⟧**。
- **cold（启动后第一次）**：0.25 s/子图量级（16→3.26 s、26→5.75 s）。这是 **zip 解压 + meta 解析**，页缓存热后消失。

### 1.3 外推到 17 片

17 片 × 26 子图 = **442 子图**：
- **warm 启动 ≈ 0.24 + 0.010×442 = 4.7 s** ✅ 命中负责人 ≤5 s 目标
- **cold 首次启动 ≈ 0.25×442 ≈ 110 s**（一次性，页缓存热后不再付）

对照原官方 VitisAI EP 路线 **425.5 s**：warm 快 **≈90×**，cold 快 **≈3.9×**。

**注意**：这个 4.7 s 是**线性外推**，不是 17 片实测（见 §5）。1→26 的区间内曲线是平的，外推到 442 属于合理但有风险的外推。

## 2. B3 — M=96 定案

`sd_fastpm_DiT.zip⟧ 里 1,233 个 gemm 事务，去重后 **293 个 (B,M,K,N) 组合**。

**M 的全部取值（49 个）**：

```
1, 2, 160, 256, 576, 768, 832, 960, 1024, 1200, 1216, 1280, 1344, 1456, 1536, 1600,
1728, 1792, 1856, 1920, 1984, 2048, 2240, 2304, 2560, 2688, 3072, 3136, 3328, 3840,
4096, 4352, 4800, 5120, 5376, 6144, 6400, 6912, 7168, 7680, 8192, 8960, 9216, 10240,
10752, 12288, 12544, 15360, 16384
```

**没有 96，也没有 64 或 128。** layernorm 的 M 集合同样从 160 起。

⇒ **M=96 必须 pad 到 160**（M 维 1.67× 工作量；N/K 不变）。
备选是现场生成 96 档事务，但那要 AIE 编译器（历史 350–380 s/片），与本轮"启动压下来"的目标冲突。

**这意味着**：即使启动降到 4.7 s，**每图的扩散计算会因为 1.67× 的 M padding 变慢**。
如果原 8 步是 8.67 s（M=96 原生），pad 到 160 后粗估 ≈14.5 s——**会吃掉启动收益**。
这是本轮最重要的**新风险**，必须在下结论前实测（见 §5）。

## 3. B2 — 服务化加固

### 3.1 两个崩溃点

| 崩溃 | 触发 | 性质 |
|---|---|---|
| `0xC0000409⟧ | EP 用完后，**进程退出时异步触发** | 即使调 `os._exit(0)⟧ 也拦不住；产物已落盘 |
| `0xC0000409⟧ | `load_state⟧ 传**不存在的文件** | E1-N1；不报错、直接打死进程 |

### 3.2 采用的模式（`_scratch/dd_worker.py⟧）

```
client                           worker (独立进程)
  ├─ 预检 state: exists + sha256   ├─ 建 EP 会话 (dd_cache 命中)
  ├─ spawn 进程                    ├─ run
  ├─ 等退出                        ├─ 写 result.json (含 out_sha256)
  └─ 判据 = 产物在不在，不是退出码  └─ os._exit(0)（仍可能被异步崩溃覆盖）
```

**核心判据**：`result_written⟧ 才是成功信号，**退出码不可信**。
这与 E1 的教训同构：`load_state⟧ 不校验路径、`save_state⟧ 空跑也返回成功——**官方 API 的返回值不是信号，产物才是**。

### 3.3 实测（26 子图图，4 个独立 worker）

| 项 | 结果 |
|---|---|
| 成功 | **4/4** |
| **输出 sha256** | `b69dae56a14d1a83…⟧ **四进程完全一致** |
| 会话 | 0.510 / 0.543 / 0.544 / 0.623 s |
| run | 0.279 / 0.297 / 0.311 / 0.333 s |
| 退出码 | 四个都是 `0xC0000409⟧（被产物判据吸收） |

**跨进程确定性成立**——这对"每图精度按 mean 1.5%"的验收很关键：同一输入在不同进程给出**逐字节相同**的输出。

## 5. 为什么 ④17 片全链没跑（诚实负结果）

三条，任何一条都足以挡住：

1. **80 子图的真图加载不了。** `zimage_loop/out_fix2⟧ 有 80 个 DynamicDispatch + 80 个 meta，但加载时报
   `Failed to parse ctrl pkt meta JSON String: parse error at line 4, column 5: unexpected ']'⟧
   （Op `/blocks.0/attention_norm1/Mul⟧，`SDMul_bfp⟧）。根因是**项目自己打的** `sd_fastpm_ours*.zip⟧ 里
   `*_ctrl_meta.json⟧ 是坏的（我早前扫到过 65 B 的版本）。**这是历史遗留的坏件，不是本轮引入。**
2. **17 片需要重新导出**（`_probe_out/shards⟧ 2026-10-11 前已删）。导出 22 GB ONNX + 逐片分区，
   按本轮实测的 0.9 s/子图，442 子图 ≈ 7 min 分区，但导出本身是另一件事。
3. **B3 让"17 片全链"的结论可能反转**：M=96 要 pad 到 160，每图计算 +67%，
   在实测之前跑全链只能得到"启动 4.7 s"，得不到"每图 8.3 s"。

**建议下一步顺序**：先做 **M=160 vs M=96 的单算子计算量实测**（决定 8.3 s 还成不成立），再决定要不要投入导出。
