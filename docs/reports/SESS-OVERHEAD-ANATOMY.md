# SESS-OVERHEAD-ANATOMY — 官方路线会话开销四段解剖 + 常驻会话复评

> **任务** t22_sessA（2026-10-24）。重开项目最古老的问题：
> 官方路线（VitisAI EP + `.rai`）算一张 128×128 / 8 步图只要 **8.67 s**，
> 但会话启动要 **几百秒**。本文把这几百秒逐段打点、给出可缓存性判定、
> 并用摊销模型回答「当年若按一次性 CLI 测，结论会不会完全不同」。
>
> 所有历史数字都追溯到原始日志（`file:line`）；所有今日数字都是本机实跑。
> 预测先行、负对照、诚实负结果见 §6 / §5.4。

---

## 0. 结论先行

1. **「几百秒」不是编译，也不是 HW context，而是「每参数 ~50–70 ns 的单核 CPU 权重镜像装载」。**
   17 个分片 × 361.8 M 参数 = 6.15 B 参数 → 实测 **257.1 s（安静机器）/ 425.5 s（负载机器）**，
   折算 **41.8 / 69.2 ns/param**。同一速率在 39.3 M、60 M、353.9 M、361.8 M 四个模型上复现（§2.3）。
2. **编译（①）确实是 350–380 s/片、17 片 ≈ 95–108 min，但它被 `.rai` 完整缓存**；
   热会话期间「0 new, 0 modified」——**①在稳态下是 0**。
3. **HW context/partition（②）几乎是免费的**：跨拓扑拟合给出的固定项 ≈ 0.13 s。
   任务书假设②是主成本，**实测否证**（§2.2、§6-F2）。
4. **JIT/首跑（④）= 0**：首跑 0.065 s vs 稳态 0.062 s（1.0×）。今日复测 4.45 ms vs 2.80 ms（+1.6 ms）。
5. **常驻会话复评：warm 后每图 8.3 s —— 预测的「8–9 s 级」被历史数据直接证实。**
   证据是当年一个**从未按这个角度读过**的日志：`batch.log` 里「2 image(s) in ONE process」，
   第 2 张图 **8.3 s**，而 17 个会话建了 257.1 s。
6. **一次性 CLI 会把结论反转**：N=1 时官方路线 **265.4 s/图**，比开放栈的 96.9 s **慢 2.74×**；
   只有 N ≥ 10–19 张（同一常驻会话内）官方路线才反超。所谓「快 3×」是**纯计算**比值
   （8.67 s vs 27.73 s = 3.20×），不是端到端比值。

## 2. 四段解剖

会话开销 = ①编译 + ②上下文创建 + ③权重装载/量化 + ④JIT/首跑。
下表把「一次性」与「每会话」分开列——这是本文最重要的口径区分。

| 段 | 内容 | 实测秒数（6.1B / 17 片） | 证据 | 产物可落盘复用？ | 会话可常驻消掉？ |
|---|---|---|---|---|---|
| **① 编译** | 图 → xclbin/控制码/量化权重 | **冷：5,950–6,460 s**（17 × 350–380 s，≈95–108 min）<br>**热：0 s**（0 new / 0 modified） | `HANDOFF.md:319`；`STATIC-SHAPE-ENGINEERING.md:341` | **是**——`.rai` 按图哈希落盘 | 不适用（已缓存） |
| **② 上下文创建** | HW context / partition 建立 | **≈0.13 s 固定项**（跨拓扑拟合），不是主成本 | §2.2 拟合；`SESSION-COST-ATTRIBUTION.md:46-50` | **否**（官方栈无会话序列化） | **是** |
| **③ 权重镜像装载** | 416 MB `bfp16ebs8` 镜像 → NPU BO | **每会话 15.1 s（安静）/ 25.0 s（负载）**<br>17 片 = **257.1 / 425.5 s** | `batch.log`、`_prof128.log` | **否**（每次建会话都重做） | **是** |
| **④ JIT/首跑** | 第一次 `sess.run` | **≈0**（0.065 vs 0.062 s；今日 +1.6 ms） | `_firstrun.log:19-31` | 不适用 | 不适用 |
| — | 其它（ONNX parse / 磁盘 / VAE） | parse 2.4 s/会话；磁盘 0.23 s/会话；VAE 0.57 s/图 | 同上 | parse 不可缓存 | VAE 已常驻 |

### 2.1 ① 编译 —— 大、但完全可缓存，稳态为 0

- 冷编译按**片**计价：S=96 几何 **350–380 s/片**（`HANDOFF.md:319`；删缓存后现场重编译 `353.8 s`，:347）。
  17 片 ≈ **95 min**（`STATIC-SHAPE-ENGINEERING.md:341` 用 `.rai` 写入时间戳间隔反推）。
- 几何放大后爆炸：S=1056（512×512）**764.5 / 777.6 / 1173.1 / 1193.1 s/片**（`HANDOFF-512.md:135-140`）；
  3-block 单图 **995.5 s**（`SINGLE-GRAPH-LIMITS.md:102`）；YOLOv4 整网 **1973.97 s**（`YOLO-ON-NPU.md:37`）。
- **产物实测（本文今日新做，之前没人拆过）**——唯一存活的厂商件
  `vendor_artifacts/39e41383350b8c53e90996269478cfb7.rai`（418,881,856 B）：

  | 区段 | 字节 | 占比 | 是什么 |
  |---|---:|---:|---|
  | 头部/元数据 | 282,432 | 0.07% | 子缓冲表、shape、28 个 region 偏移 |
  | **`coalesed_weights` 权重镜像** | **416,071,680** | **99.33%** | **已经是 `bfp16ebs8`** |
  | 尾部控制码 | 2,527,744 | 0.60% | `ctrl.elf`（偏移 24）+ `xclbin`（尾部偏移 2,415,710） |

  **结论：①的产物 99.33% 是权重，控制码只占 0.60%（2.5 MB / 2 个 block）。**
  编译花 350–380 s 换来的「代码」只有 2.5 MB，其余时间花在**把 fp32 权重量化成 bfp16 并排成 vendor 布局**上。
- **可缓存性：是**。热会话期间 `vaip cache files written during creation: 0 new, 0 modified`
  （`SESSION-COST-ATTRIBUTION.md:41`、`_attrib.log:24`）——**①在稳态下严格为 0**。
- **今日负结果**：缓存目录 `C:\temp\<user>\vaip\.cache` 在 workspace-write 沙箱下**不可写**
  （实测 `WRITE DENIED` / `MKDIR DENIED`），`XLNX_CACHE_DIR` 指向工作区时**也没有产出 `.rai`**
  （`cache_files_after: 0`）。见 §5.4。

### 2.2 ② 上下文创建 —— 任务书假设的主成本，实测不是

任务书把「HW context/partition」列为一段。实测把它压到很小：

- 跨 6 个模型（39.3 M / 60 M / 353.9 M / 361.8 M / 2.36 M / 0.59 M）拟合 `t = a + b·params`，
  **固定项 a ≈ 0.13 s**（0.037 M 参数的 res3x3 仍要 0.13 s）。
- 也就是说：**「建一个 HW context」本身是 0.1 s 量级，不是几十秒。**
- 那 15–26 s 去哪了？见 ③。

### 2.3 ③ 权重镜像装载 —— 几百秒的真身

- **速率恒定**（`session_cost.json` 的四个 ≥39 M 参数点）：

  | 参数 | 实测热会话 | ns/param |
  |---:|---:|---:|
  | 39.3 M | 2.35 s | 59.8 |
  | 60 M | 3.0 s | 50.0 |
  | 353.9 M | 21.0 s | 59.3 |
  | 361.8 M | 25.0 s | 69.1 |
  | **6.15 B（17 片合计）** | **257.1 s（安静）/ 425.5 s（负载）** | **41.8 / 69.2** |

- **速率与图拓扑无关**：YOLOv4（数百节点、卷积为主）与单 GEMM（1 个节点）给出同样的 ~50–60 ns/param。
  这排除了「按节点数计价」的图分析，指向**按参数个数扫权重**。
- **与归因报告一致**：EP 侧占 86.6%，且是 **90–102% 单核 CPU**（`20.15 s wall / 20.38 s CPU`，
  `SESSION-COST-ATTRIBUTION.md:55-56`），**不是磁盘等待**（磁盘只占 1.2%）。
  361.8 M 参数 ÷ 17 s ≈ **21 M 权重/s**，即 ~47 ns/权重——与上表同量级。
- **量化发生在①，不在③**。`.rai` 里的权重**已经是 bfp16ebs8**，
  且被逐字节验证过：`imaggers/weights/FINDINGS.md` §3c 用独立打包器重建两个 block，
  与 `.rai` 的 `coalesed_weights` **416,071,680 / 416,071,680 B 完全相同、0 差异**。
  所以③是**装载**（把已量化镜像搬进 NPU BO），不是「现场量化」。
  任务书把「③权重装载/量化」写在一起，实测应当拆开：**量化 ∈ ①，装载 ∈ ③**。
- **可缓存性：否**。每次 `InferenceSession()` 都重做一遍；`.rai` 只免掉①，不免③。
  这解释了为什么「缓存命中」了还要 15–26 s。
- **旁证（字节假说）**：同一 361.8 M 参数的 build A（fp32 存 ONNX，1.35 GiB）比 build B
  （fp16 存 ONNX，0.72 GiB）慢约 2×（`_sessbreak128.log` 25.24 s vs `_sessbreak.log` 14.28 s，
  同日相隔 4 分钟）。若③真是「按参数个数」，两者应当一样快；实测差 1.8–2.2×，
  更贴合 **ONNX 存储字节数**（1.87×）。**这一条与「50 ns/param」部分冲突，未解决，列为开口**（§6-F4）。

### 2.4 ④ JIT/首跑 —— 0，没有可赚的

- 单分片直测（`_firstrun.log`）：`InferenceSession() 17.51 s`，**首跑 0.065 s**，
  稳态 0.062 / 0.061 / 0.064 s，`first/steady = 1.0x`。
- 当年项目自己的结论：**「首次运行不贵，『第一次用到某片』才贵——贵在建会话」**（`MEMORY-AND-TIMING.md` §一）。
- 今日复测（test_model.onnx）：首跑 4.45 ms，稳态 2.80 ms，差 **+1.6 ms**——相对 28.6 s 的会话成本是 **0.006%**。

## 3. 摊销模型

### 3.1 模型

会话开销一次性、每图摊销：

```
T(N) = C + N · t          C = 会话开销（② + ③，一次性）
                           t = warm 后每图耗时
每图成本 = T(N) / N = C/N + t
```

实测取值（全部来自原始日志，不是估算）：

| 机器状态 | C（17 会话） | t（每图） | 来源 |
|---|---:|---:|---|
| 安静（20.8 GiB 可用） | **257.1 s** | **8.3 s** | `batch.log` 图2 |
| 负载（20.1→5.3 GiB） | **425.5 s** | **9.24 s**（8.67 计算 + 0.57 VAE） | `_prof128.log` |

### 3.2 每图成本曲线

| N（同一常驻会话内跑几张） | 安静机 T(N) | 安静机 每图 | 负载机 T(N) | 负载机 每图 |
|---:|---:|---:|---:|---:|
| 1 | 265.4 s | **265.4 s** | 434.7 s | **434.7 s** |
| 2 | 273.7 s | **136.9 s** | 444.0 s | 222.0 s |
| 4 | 290.3 s | 72.6 s | 462.5 s | 115.6 s |
| 8 | 323.5 s | 40.4 s | 499.4 s | 62.4 s |
| 12 | 356.7 s | 29.7 s | 536.4 s | 44.7 s |
| 16 | 389.9 s | 24.4 s | 573.3 s | 35.8 s |
| 32 | 522.7 s | 16.3 s | 721.2 s | 22.5 s |
| 64 | 788.3 s | 12.3 s | 1016.9 s | 15.9 s |
| 128 | 1319.5 s | 10.3 s | 1608.2 s | 12.6 s |
| ∞ | — | **8.3 s** | — | **9.24 s** |

曲线形状：**前 8 张吃掉 60% 的收益**（265→40 s/图），N>32 后基本贴地（≤16 s/图）。

### 3.3 盈亏平衡 vs 开放栈

开放栈（本项目 webui，128²/8 步）：**loop 27.728 s**、首 job 总计 **96.857 s**（`README-WEBUI.md` §8，job 20261018-170459-ed2a32）。

- **纯计算**：官方 8.67 s vs 开放 27.73 s = **3.20×** ← 这就是「快 3×」的真身
- **端到端 N=1**：官方 265.4 s vs 开放 96.9 s = 官方**慢 2.74×**
- **盈亏平衡**（官方 C + N·t ≤ 开放 N × 27.73）：
  - 安静机 C=257.1 → **N ≈ 10 张**
  - 负载机 C=425.5 → **N ≈ 19 张**

**所以「3×」只在两种口径下成立：纯计算，或 N ≥ 10–19 的常驻会话。**
任何一次性 CLI 口径都会得出「官方路线更慢」的相反结论。

### 3.4 当年若按一次性 CLI 测，结论会如何不同

| 口径 | 官方路线 | 开放栈 | 结论 |
|---|---:|---:|---|
| 纯计算（8 步） | 8.67 s | 27.73 s | 官方 **快 3.20×** |
| 一次性 CLI（N=1） | 265.4 s | 96.9 s | 官方 **慢 2.74×** |
| 常驻会话（N=8） | 40.4 s/图 | ~28 s/图 | 官方 **慢 1.4×**（还没回本） |
| 常驻会话（N=32） | 16.3 s/图 | ~28 s/图 | 官方 **快 1.7×** |
| 常驻会话（N→∞） | 8.3 s/图 | ~28 s/图 | 官方 **快 3.4×** |

**「官方路线 3× 快」与「官方路线 2.7× 慢」是同一个系统的两个口径，差别全在 C 有没有被摊掉。**

## 4. 可绕性结论

| 段 | 能否绕过 | 手段 | 代价 | 证据 |
|---|---|---|---|---|
| **① 编译** | **已绕过** | 直接分发 `.rai`（419 MB/片，含 416 MB 权重镜像） | 换权重/换几何要重编 350–380 s/片；512² 要 764–1193 s/片 | `.rai` 结构实测（§2.1） |
| **② 上下文** | 本来就不贵 | — | — | 固定项 ≈0.13 s |
| **③ 权重装载** | **只能靠「不重建会话」** | ①同进程跑 N 张图（已实测 8.3 s/图）；②合并分片 17→5 把 ③ 砍到 ~1/4 | 合并需冷编译 2–3.5 h，且每会话固定内存 0.522 GiB 不降 | `batch.log`；`MEMORY-AND-TIMING.md` §三 |
| **④ JIT** | 无可绕 | — | — | 0 |
| **跨进程常驻** | **不可行** | 官方栈无会话序列化（`.rai` 只是编译产物，不是会话状态） | 服务必须把**器件进程活着**，不能「存盘再起」 | 建会话 0 文件写入 + 每次全价 |

**一句话**：官方路线的会话开销**不可缓存、不可序列化、只能常驻**。
唯一的正解就是任务书说的 webui 服务式长会话——而这恰恰是当年一次性 CLI 测法看不见的。

**给本项目的直接含义**：开放栈（IRON/XRT）现在每图 27.7 s，其「启动/载荷」只有 37.7 s、
且没有 ③ 这种 O(参数) 的重复装载（权重由我们自己的 host 侧打包，逐层读、可 `--cache-all`）。
**官方路线的优势区间是「大批量、单会话、固定几何」；开放栈的优势区间是「小批量、任意几何、可改图」。**
两者不是同一条曲线上的点，是两条斜率不同的线。

## 5. 今日复测（2026-10-24，本机实跑）

### 5.1 方法

`imaggers/sessA_probe.py` / `sessA_attr.py` / `sessA_cfg.py`：
对每个模型，在**空缓存目录**下建会话（冷），再在同进程内连续建 3 次（热），
中间穿插 N 次 `sess.run`；同时统计缓存目录的文件数与字节数增量；
CPU EP 同模型做负对照；`enable_profiling` 取节点级 provider 归属。

模型：`C:\RyzenAI\1.8.0\quicktest\test_model.onnx`（AMD 随包，23.6 MB，**23.6 M 参数 / 386 节点**）。
环境：Python 3.12.11、`onnxruntime 1.27.0`、providers `[VitisAI, Dml, CPU]`、`RYZEN_AI_INSTALLATION_PATH=C:\RyzenAI\1.8.0`。

### 5.2 结果

| 量 | 实测 | 备注 |
|---|---:|---|
| `import onnxruntime` | 0.526 s | |
| 磁盘读 23.6 MB | 0.009 s | |
| `onnx.load` 解析 | 0.166 s | |
| **冷建会话（空缓存）** | **23.27 s** | |
| **热建会话 ×3（同进程）** | **24.91 / 30.16 / 28.64 s** | **没有变快** |
| **建会话期间写入缓存** | **0 文件 / 0 字节** | 冷热都是 0 |
| 首跑 | 4.45 ms | |
| 稳态 run（16 次） | 2.55–3.17 ms，均值 **2.80 ms** | 平坦，无漂移 |
| **CPU EP 会话（负对照）** | **0.138 s** | |
| CPU EP run（负对照） | 12.1 ms | |

**比值**：会话 28.6 s ÷ 单次推理 2.80 ms ≈ **10,200 : 1**；NPU 会话 ÷ CPU 会话 = **207×**。
在 16 次推理的负载上，会话占 **99.85%**。

### 5.3 负对照（必配）

1. **CPU EP**：同模型 0.138 s vs NPU 28.6 s → 这 28 s **是 NPU/EP 路径特有**的，不是 ORT 通用开销。
2. **profiling 归属**：3/3 节点在 VitisAI EP，排除「其实全跑 CPU」的误判。
3. **两次独立配置**（无 opts / 带 `config_file=vaip_config.json`）：29.36 s vs 29.82 s，**无差异**，
   排除「少传 config 导致退化」的解释。

### 5.4 诚实负结果（三条）

**N1 —— 今日无法把①与③分开，因为缓存根本写不进去。**
`C:\temp\<user>\vaip\.cache` 是官方栈的默认缓存根（`vaip_env.py` 文档 + `test7\cache\clear` 同源证据）。
本会话是 workspace-write 沙箱，实测该路径**写拒绝**：

```
WRITE DENIED: 对路径"C:\temp\<user>\vaip\.cache\sessA_write_test.txt"的访问被拒绝。
MKDIR DENIED: 对路径"sessA_probe_dir"的访问被拒绝。
```

`XLNX_CACHE_DIR` 指到工作区（可写）后，冷/热会话**仍然 0 文件产出**，
且热会话不比冷会话快——**说明该变量在本机这次调用里没有把 `.rai` 落盘**。
这与 `vaip_env.py` 声称的「redirects the whole compile tree」**不一致**，记为开口。
后果：本机今日的 28 s 是**每次重建**（含内存内编译），**不能**用来测「热会话残值」。
历史热会话残值（15–26 s）仍以 `_prof128.log` / `batch.log` 为准。

**N2 —— 今日小模型不可与 6.1B 外推。**
23.6 M 参数的会话 28.6 s，按 50 ns/param 应只有 ~1.3 s；差 20×，
因为它是**无缓存冷编译**而非热装载。**不能**拿它算每参数速率。

**N3 —— 「50–70 ns/param」与「字节假说」冲突，未解决。**
build A（fp32 存）比 build B（fp16 存）慢 2×，而参数个数相同。
若③纯按参数计价，两者应同速。可能解释：③按 **ONNX 存储字节**计价（1.87× 更贴合 1.8–2.2× 实测），
或两台次机器负载不同。**现有证据无法分离**，需一次「同参数、异存储格式、同机次」的 A/B（当年
`probe_slen_scaling.py` 想做的正是这件事，输出已丢失）。
